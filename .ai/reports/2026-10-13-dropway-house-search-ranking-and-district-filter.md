## Root cause — Search Ranking
`src/app/houses/page.tsx` (ก่อนแก้):

- `rankHouse()` รวมคะแนนของ **ทุกฟิลด์** (full_name ×3, address ×4, phone ×2,
  note ×1) เป็นก้อนเดียว **และ** เอา bonus ของเลขบ้าน (`hnScore * 4`) บวกเข้าไป
  ในก้อนเดียวกัน (บรรทัดราว 118–127 เดิม)
  → รายการที่ตรงเฉพาะเบอร์โทรหรือข้อความอื่นสามารถมีคะแนนสูงกว่า/แซงรายการที่ตรง
  เลขบ้านได้ ตามที่ผู้ใช้รายงาน
- ไม่มีการแยก "ระดับ" ของเลขบ้านเป็นสเกลที่ชัดเจน จึงไม่มีการจัดกลุ่ม
  "หลักน้อยก่อนหลักมาก" (15 กับ 105 อยู่ระดับเดียวกัน)
- `rankResults()` **กรองซ้ำ** หลังจากมีการกรองไปแล้วหนึ่งครั้งใน `useEffect`

## พฤติกรรมที่เปลี่ยนไป
1. **แยกคะแนนเลขบ้านออกจากคะแนนข้อความ**
   - `rankHouseNumberMatch()` ให้คะแนนเป็น "ระดับ" อยู่บนฐาน `HOUSE_NUMBER_BASE`
     (1,000,000) ซึ่งสูงกว่าเพดานคะแนนข้อความ (`MAX_TEXT_SCORE` = 10,000) เสมอ:
     - exact — เลขบ้านตรงทั้งค่า (5 → "5")
     - subForm — รูปแบบย่อย/ต่อเนื่อง (5 → "5/1", "5/2")
     - prefix — เลขบ้านที่มีคำค้นเป็นส่วนต้น (5 → "55", 12 → "125")
     - contains — มีคำค้นอยู่ภายใน เรียง **จำนวนหลักน้อยก่อน** (15 ก่อน 105)
   - `rankTextFields()` คิดคะแนนชื่อ/ที่อยู่/เบอร์/หมายเหตุ เฉพาะฟิลด์ที่ผู้ใช้เปิด
     และถูกจำกัดเพดานไว้ จึงแซงรายการที่ตรงเลขบ้านไม่ได้
2. **เลขบ้านอ่านจาก `address` เท่านั้น** — ไม่มีทางดึงตัวเลขจาก `phone` มาเป็นเลขบ้าน
   และจะไม่คิดคะแนนเลขบ้านเมื่อผู้ใช้ปิดช่องค้นหา "ที่อยู่" (`searchInAddress = false`)
3. **กรองอำเภอแบบเข้มงวด** ด้วย `extractDistrict()`
   - อ่านเครื่องหมายอำเภอจริงจากที่อยู่: `อ.` หรือ `อำเภอ` (รองรับ `อ. แม่สอด`,
     และ `อ.วังเจ้าจ.ตาก` ที่ไม่มีช่องว่างหน้า `จ.`)
   - เทียบแบบ **ทั้งชื่อตรงกัน** (`===`) ไม่ใช่ `includes` → คนละอำเภอไม่ถูกมองเป็นเดียวกัน
   - ที่อยู่ที่ไม่ระบุอำเภอ (`extractDistrict() === null`) จะ **ไม่** ถูกจัดเข้า
     อำเภอที่เลือกโดยการเดา
   - เลือก "ทั้งหมด" → ไม่กรองอำเภอ (พฤติกรรมเดิม)
4. **คืนตัวกรองที่หลุดไปทั้งหมด** และจัดลำดับ pipeline ใหม่ให้ชัดเจน:
   (1) อำเภอ/พื้นที่ → (2) ตัวกรองเดิม (พิกัด, เลขบ้าน, เบอร์, หมู่, ตำบล,
   อำเภอ(ข้อความ), จังหวัด) → (3) ค้นหาข้อความตามฟิลด์ที่เปิด → (4) จัดอันดับ →
   (5) แบ่งหน้า
   - การจัดอันดับทำ "หลัง" การกรอง และ **จัดอันดับไม่เคยเพิ่มรายการ** จึงดึงรายการจาก
     อำเภออื่นกลับมาไม่ได้
5. **การกรองทำครั้งเดียว** — ย้ายการค้นหาข้อความไปที่ `matchesSearch()` และให้
   `sortByRelevance()` ทำหน้าที่เรียงลำดับเท่านั้น (ไม่กรองซ้ำ)
6. **stable sort ชัดเจน** — ใช้ index เดิมเป็นตัวตัดสินสุดท้าย
   (`b.score - a.score || a.index - b.index`) คะแนนเท่ากัน = ลำดับเดิมเสมอ
7. ทุกครั้งที่คำค้น/อำเภอ/ตัวกรอง/ข้อมูลเปลี่ยน → `setCurrentPage(1)` (pagination
   กลับหน้า 1) และ dependency array ครบถ้วน

### หมายเหตุการออกแบบ (ควรรับทราบ)
เมื่อค้นหา "5" ลำดับที่ได้จริงคือ
`5 → 5/1 → 55 → 15 → 45 → 105 → 125 → 135`
กล่าวคือ "55" (ตรงส่วนต้น, ระดับ prefix) มาก่อน "15"/"45" (ตรงกลาง, ระดับ contains)
ตามนิยามระดับในโจทย์ ("prefix" อยู่เหนือ "contains") — ยังคงเป็นไปตามเงื่อนไขที่ให้
ไว้ทั้งสองข้อ (กลุ่มที่ตรงกับ "5" มาก่อน และ 2 หลักมาก่อน 3 หลัก) และโจทย์ระบุว่า
ตัวอย่างเป็น "ประมาณนี้"

## ปัญหาที่ยังเหลือ / ยังตรวจสอบไม่ได้
1. **BLOCKED — ข้อมูลอำเภอในฐานข้อมูลจริง**: โค้ดเดิมก็ใช้ `address.includes("อ." + district)`
   อยู่แล้ว ดังนั้นสมมติฐานคือข้อมูลจริงมีรูปแบบ `... อ.<อำเภอ> ...` แต่ **ยังไม่สามารถ
   ตรวจฐานข้อมูลจริงได้จาก environment นี้** หากมีบ้านที่ที่อยู่ไม่มีเครื่องหมาย `อ.`
   บ้านเหล่านั้นจะไม่ปรากฏเมื่อเลือกอำเภอ (ตามกติกา "ห้ามเดา") — ควรตรวจด้วย
   `select address from houses limit 50` เพื่อยืนยันรูปแบบจริง
2. **BLOCKED — การทดสอบ interaction บนเบราว์เซอร์จริง**: environment นี้ไม่มี
   browser session ที่ล็อกอิน จึงยืนยันได้แค่ระดับ source + logic harness + build
   ไม่ได้คลิก dropdown อำเภอจริง
3. **BLOCKED — Supabase RLS/ownership**: ยังไม่เคยตรวจได้จาก environment นี้
   (ไม่เปลี่ยนในงานนี้)
4. **ไม่มี test runner ในโปรเจกต์** — harness ที่ใช้ตรวจเป็นไฟล์ชั่วคราว ไม่ได้ commit
   (การเพิ่ม tsx/test runner เป็น devDependency ถือเป็น change ที่ใหญ่กว่าและมีผลต่อ
   `package-lock.json` ที่ยังไม่ถูก track จึงไม่ทำในงานนี้)
5. **ตัวกรอง `districtFilter` (ช่องข้อความ "อำเภอ")** ยังใช้ `address.includes()`
   ตามเดิม เพราะเป็นช่องค้นหาข้อความอิสระที่ผู้ใช้พิมพ์เอง ไม่ใช่ตัวเลือกอำเภอจาก
   dropdown — งานนี้แก้เฉพาะตัวเลือกอำเภอ (`selectedDistrict`) ให้เข้มงวด
6. ลำดับ "55" ก่อน "15" เมื่อค้นหา "5" ตามนิยามระดับ prefix > contains
   (ดูหัวข้อ "หมายเหตุการออกแบบ") — หากต้องการให้ "55" อยู่ในกลุ่มเดียวกับ
   "15/45/55" แบบจัดตามจำนวนหลักล้วน สามารถปรับได้
